# 실지출 트래커 — 설계 문서

작성일: 2026-10-30

## 1. 목적

토스뱅크 등 은행 앱은 "내가 한 번에 결제 → 친구들이 내 몫 외 금액을 송금"하는 상황에서
결제는 지출, 친구 송금은 수입으로 따로 기록한다. 그래서 **실제로 내가 쓴 돈**을 알 수 없다.

이 앱은 거래내역 파일을 업로드받아 AI 에이전트(Claude)로
1. 각 지출을 카테고리로 분류하고,
2. 더치페이 정산 입금을 원래 결제에 연결해 **실지출 = 결제액 − 정산 입금**을 계산하며,
3. 일별 실지출, 카테고리별 집계, 주간 절약 보고서를 대시보드로 보여준다.

### 성공 기준
- 거래내역 업로드 후 이번 달 실지출이 정산을 반영한 금액으로 표시된다.
- 정산 후보가 "확인 대기"로 제안되고, 사용자가 확정/수정/거절할 수 있다.
- 일별 실지출 차트, 카테고리별 차트가 보인다.
- 주간 보고서가 예산 대비·지난 주 대비로 줄일 수 있었던 카테고리를 구체적으로 제시한다.

### 범위 밖 (YAGNI)
- 은행 API 자동 연동, 로그인/다중 사용자, 모바일 앱, 이메일·푸시 알림.

## 2. 결정 사항

| 항목 | 결정 |
|---|---|
| 데이터 입력 | 엑셀(.xlsx) / CSV 업로드 |
| 형태 | FastAPI 백엔드 + 정적 HTML/JS 프론트(Chart.js, 빌드 없음), 로컬 실행 |
| 저장소 | SQLite 파일 (`data/app.db`) |
| AI | Claude API (`anthropic` Python SDK), 키는 `.env`의 `ANTHROPIC_API_KEY` |
| 정산 | 규칙으로 후보 생성 → Claude가 매칭 제안 → 사용자 확인 |
| 보고서 | 대시보드 버튼으로 생성·저장, 기준은 카테고리별 월 예산 + 지난 주 비교 |

## 3. 구조

```
spending-tracker/
  app/
    main.py            # FastAPI 앱, 라우트, 정적 파일 서빙
    db.py              # SQLite 연결·스키마
    parser.py          # 파일 → 표준 거래 목록
    stats.py           # 실지출·일별·카테고리별 집계 (순수 함수)
    settle.py          # 정산 후보 생성 (순수 함수)
    agent/
      client.py        # Claude 호출 래퍼 (테스트에서 교체 가능)
      categorize.py    # 카테고리 분류 (+ 가맹점 캐시)
      match.py         # 정산 매칭 제안
      report.py        # 주간 보고서 생성
  static/              # index.html, app.js, style.css
  tests/
  requirements.txt
  .env.example
```

각 모듈은 하나의 역할만 가진다. `stats`, `settle`, `parser`는 DB·AI와 무관한 순수 로직이라 단독 테스트가 가능하다.
AI 호출은 모두 `agent/client.py`를 거치므로 테스트에서는 가짜 클라이언트로 교체한다.

## 4. 데이터 모델

- **transactions**: `id, occurred_at(datetime), description, counterparty, amount(int, 원 단위 양수), direction('out'|'in'), category, is_income(bool), source_hash(unique)`
  - `source_hash` = 일시+내용+금액+잔액 해시 → 같은 파일 재업로드 시 중복 방지
  - `is_income`: 정산이 아닌 진짜 수입(월급 등) 여부. 입금 중 정산으로 확정되지 않은 것은 수입으로 취급
- **settlements**: `id, payment_id, incoming_id, status('pending'|'confirmed'|'rejected'), reason`
  - 하나의 결제에 여러 입금이 연결될 수 있다. 하나의 입금은 최대 하나의 결제에만 확정된다.
- **merchant_categories**: `merchant(unique), category` — 분류 캐시. 사용자가 수정하면 갱신
- **budgets**: `category(unique), monthly_amount`
- **reports**: `id, week_start(date), content(markdown), created_at`

카테고리 고정 목록: 식비, 카페, 유흥, 교통, 쇼핑, 구독, 생활, 의료, 기타.

## 5. 데이터 흐름

1. **업로드** → `parser`가 열 이름을 자동 인식(거래일시/일시/날짜, 적요/내용/거래처, 거래금액/금액, 입금/출금, 거래유형 등).
   금액 부호 또는 입금·출금 열로 `direction` 결정. 인식 실패 시 Claude에게 헤더+샘플 3행을 보내 열 매핑을 받는다.
2. **분류** → 출금 거래마다 가맹점 캐시 확인, 없는 것만 묶어서 한 번에 Claude 호출 → 캐시 저장.
3. **정산 후보** (`settle.find_candidates`): 각 입금에 대해
   - 결제(출금)가 입금 시각 기준 **7일 이내 이전**에 있고,
   - 입금액이 결제액보다 작으며,
   - 입금 내용이 개인 이름처럼 보이는 송금(급여·이자·환불 키워드 제외)인 경우 후보로 묶는다.
4. **매칭 제안** → 후보 묶음을 Claude에 보내 `{incoming_id, payment_id | null, reason}` JSON을 받아 `pending`으로 저장.
   (예: 4명이 갈 만한 식당 결제 80,000원 직후 20,000원 입금 3건 → 같은 결제로 묶음)
5. **확인** → 사용자가 확정/거절/다른 결제로 변경.
6. **집계** (`stats`): 결제별 실지출 = 결제액 − 확정 정산 입금 합(최소 0). 카테고리는 결제의 카테고리를 따름.
   일별·카테고리별·월 합계 산출. `pending` 정산은 계산에 넣지 않고 "확정 시 예상 실지출"로 따로 표시.
7. **주간 보고서** → 해당 주(월~일)와 지난 주의 카테고리별 실지출, 예산(월 예산 ÷ 해당 월 일수 × 7), 상위 지출 항목을
   Claude에 보내 마크다운 보고서(요약, 예산 초과 카테고리, 지난 주 대비 증가, 구체적 절약 제안)를 받아 저장.

## 6. 화면

단일 페이지, 탭 구성:
- **대시보드**: 이번 달 실지출(큰 숫자), 오늘 실지출, 일별 막대 차트, 카테고리 도넛 차트, 예산 대비 진행 막대
- **업로드**: 파일 선택 → 처리 결과(추가 n건, 중복 n건, 정산 후보 n건)
- **정산 확인**: pending 목록 — 결제 / 입금 / AI 이유 / 확정·거절 버튼, 확정 정산 목록
- **거래내역**: 목록, 카테고리 드롭다운으로 수정(가맹점 캐시도 갱신)
- **예산**: 카테고리별 월 예산 입력
- **주간 보고서**: 주 선택 → 생성 버튼, 저장된 보고서 보기

## 7. 오류 처리

- API 키 없음/호출 실패: 분류는 '기타', 매칭 제안은 생략하고 화면에 경고 표시. 수동 분류·수동 정산 연결은 계속 가능.
- 파일 형식 인식 실패: 어떤 열을 찾지 못했는지 에러 메시지로 반환.
- Claude 응답 JSON 파싱 실패: 1회 재시도 후 실패 처리.

## 8. 테스트

- `parser`: 샘플 CSV/XLSX(입출금 분리형, 부호형) → 표준 거래
- `settle`: 후보 생성 규칙 (7일 경계, 금액 조건, 제외 키워드)
- `stats`: 정산 반영 실지출, 일별·카테고리 집계, pending 제외
- `agent`: 가짜 클라이언트로 분류 캐시 동작, 매칭 JSON 저장
- API: FastAPI TestClient로 업로드→확정→대시보드 흐름 한 번
